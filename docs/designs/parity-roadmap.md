## Problem Statement
The founder wants Hopshot "close to macshot and CleanShot" feature-wise. Today Hopshot does area and full-screen capture, a floating shelf, drag into any app, copy, phone send (end-to-end encrypted), phone-to-computer upload and auto-cleanup, on Mac and Windows. It has no markup, window capture, OCR, scrolling capture or recording. Switchers from CleanShot (Mac) and Snipping Tool/ShareX (Windows) expect those, so the comparison pages have to list them as missing.

This reverses decision D2 in `docs/designs/cleanshot-gaps.md` (23 Nov 2026: markup and OCR stay PRD §3.3 non-goals until a Hopshot user asks). The reversal is deliberate: the founder chose full parity on 24 Nov.

## Demand Evidence
- 1 paying customer: a stranger on Windows who installed v0.1.13 and paid within about 2 minutes on 20 Nov. They paid without markup or window capture.
- That install has not reported since 20 Nov. No install has reported since 20 Nov 10:14 UTC (`claude/funnel-check-2026-11-23.md`). Whether the ping works on 0.1.14 is unverified.
- 7 installs ever, mostly the founder's. About 115 X link replies produced 0 sales.
- No feature request from a Hopshot user yet. Markup asks came from CleanShot users on X.

## Status Quo
- Windows: Snipping Tool is built in and free, with Quick markup, Text Extractor (OCR), redaction and video. ShareX is free and open source with 30+ annotation tools, scrolling capture and OCR, but users call it "too complicated".
- Mac: macshot is free and GPLv3 with 19+ annotation tools, window snap, scroll capture, beautify, recording, OCR + translation, pin and history. CleanShot X is the paid leader ($35 + $19/year for updates).
- Nobody owns the step after capture: getting the screenshot into a web app, an AI chat or a phone across Mac and Windows without files piling up.

## Target User & Narrowest Wedge
- Who: people who paste screenshots into web apps and AI chats all day, on Windows or on a Mac + PC mix. The one buyer so far is on Windows. No named user yet.
- Wedge: "CleanShot for Windows". Markup and window capture land on the shelf, ready to drag. The same code ships on Mac.

## Constraints
- Solo founder; Ship or Die ends 16 Dec 2026 (22 days).
- Tauri v2: Rust owns logic, thin React UI. Platform code lives behind `platform/macos.rs` and `platform/windows.rs` (CLAUDE.md rules 3, 4). New dependencies need a one-line justification (rule 5). Privacy invariants (rule 1): no plaintext images or text leave the device except as HOP1 ciphertext.
- Every OS-level feature is built twice (macOS + Windows); macshot only does Mac.
- The founder has not watched a user yet.

## Premises
1. Goal: full feature parity with macshot + CleanShot X on Mac and Windows, reached in tiers. Only Tier 1 leaves PRD §3.3 now; Tier 2 and 3 become a gated roadmap (see step 1).
2. The delivery flow stays the reason to pay: every feature lands on the shelf, then drags, copies or goes to the phone.
3. Order (revised after the second opinion): verify the install ping first, then the tiers.
   - Tier 1 (by 16 Dec): window capture (0.1.15); markup core (select, arrow, rectangle, ellipse, text, pen, highlighter, numbered step, blur/pixelate, crop/rotate) and "Copy for AI" (image + on-device recognized text) in 0.2.0.
   - Tier 2: beautify, capture timer, pin-to-screen, OCR + QR + translate, auto-redact personal info, history search, scrolling capture.
   - Tier 3: screen recording (MP4/GIF, audio, click highlights) + trim editor.
4. Watching 2 users runs alongside Tier 1. Its findings can reorder Tier 2.

## Approaches Considered
### Approach A: Separate edit window from the shelf
Not chosen: a separate windowed editor with its own chrome, and no markup at capture time.
### Approach B: Layer engine with a live Rust-rendered preview
Not chosen for Tier 1: rendering every pointer move through Rust (a live preview pipeline plus layer compositing) is effort XL and the riskiest path to 16 Dec. Tier 1 keeps B's data model (versioned annotation document, Rust flatten) and drops only the live Rust preview.
### Approach C: Markup inside the capture overlay (chosen)
The markup toolbar lives in the overlay window, used both at capture time (Shift-release) and from the shelf (Edit).

## Recommended Approach
**Approach C**, with these decisions (D6 and D7 decided by the founder, 24 Nov):

**Commit rule (D6).** Releasing the mouse still captures instantly, as today (PRD F1.5/G1 unchanged).
- Markup is opt-in in three ways:
  - hold **Shift while releasing** (area drag, window click in window mode, click-without-drag for the monitor, or **Shift+F**);
  - **Edit** on any shelf card;
  - the Settings checkbox **Open markup tools** (off by default) in Settings → General → "After capture:", next to Copy to clipboard and Show shelf, with the helper text "Or hold ⇧ when you release." (Windows: Shift). When it is on, every capture opens the toolbar, and Enter finishes (design review D11; the label replaces "Show markup after every capture").
- With markup, F1.5's "< 500 ms on the shelf" counts from pressing Enter/Done.
- With markup, `commit` writes nothing to `captures/` and runs no part of `deliver` (clipboard copy, shelf insert, `record_capture`, vault auto-sync). On Done, Rust flattens, writes `originals/{id}.png` and `captures/{id}.png`, and then calls `deliver` once with the flattened PNG. Esc-discard delivers and records nothing (eng review S1).
- Onboarding (DESIGN S8) adds one line teaching Shift-release.
- The S2 idle hint pill teaches it on every capture (design review D4): `Drag to capture · ⇧ to mark up · Space window · F full screen · Esc cancel` (`Space window` shipped with window capture in 0.1.15), with keycaps in mono 11 px. Windows shows `Shift` instead of `⇧`.

**Plan gating (D7).**
- Markup and Copy for AI are free on every plan. No `config/limits.json` gate is added.
- A Shift-release capture counts as one capture, as today.
- Edit on an existing item is not a capture: it never calls `stats::record_capture` and does not use the Free daily cap.
- Edit and Copy for AI keep working when the Free cap has paused capture.

**Toolbar layout (design review D1).**
- Order, left to right, with a hairline divider between groups: tools (Select V, Arrow A, Rectangle R, Ellipse O, Text T, Pen P, Highlighter H, Numbered step N, Redact B, Crop C) | colour + stroke width | undo, redo | **Copy for AI** · **Done** (primary, rightmost).
- At capture time, the toolbar is centred on the selection, 8 px below it, and clamped so it stays at least 12 px inside the monitor. If there is less than 56 px below the selection, it flips 8 px above. If neither fits (for example a full-screen capture), it floats inside the selection, 16 px from its bottom edge.
- In Edit, the same bar sits 16 px below the scaled image.
- Selection (design review D12). A selected shape gets a 1 px dashed `--accent` bounding box and 8×8 white handles with a 1 px `#111` border at the corners; an arrow gets one handle at each end. These are preview-only and never flattened.
  - Drag inside the box to move, drag a handle to resize. Holding Shift keeps the ratio, or snaps an arrow to 15° steps.
  - A shape you just drew stays selected, so Delete and the colour/size controls act on it right away.
- Accessibility (design review D9), extending DESIGN §7.
  - The toolbar is `role=toolbar` with a roving tabindex: Tab enters and leaves it, ←/→ move between buttons, and Enter/Space activate the focused button. With focus outside the toolbar, Enter is still Done and Space still does nothing.
  - Every button has an `aria-label` and a tooltip that includes its key, for example "Arrow (A)". The `--focus` ring is always visible.
  - The card's "Reading text…" chip and the toasts are `aria-live=polite`.
  - With reduced motion, the toolbar, hint and Edit image appear with no fade or slide, and the capture flash is skipped as today.
  - DESIGN S2 states plainly that drawing shapes needs a pointer. Keyboard-only users can crop, finish, copy and discard.
- Annotation ink (design review D8). These values are served by `markup::geometry()` and do not change with the theme.
  - Six swatches: Orange `#FF6B2C` (default), Red `#FF3B30`, Yellow `#FFD60A` (the highlighter default, at 40% alpha), Blue `#0A84FF`, Black `#111111`, White `#FFFFFF`.
  - The picker is a one-row popover opened from the colour dot.
  - Stroke S/M/L is 2/4/8 px and text S/M/L is 16/24/36 px, both multiplied by the image scale factor (within the D6 bound of 1–64 px).
  - The last colour and size are remembered per tool for the session.
- Tokens (design review D7). The toolbar is opaque: `--surface-raised`, `--raised-border` hairline and dividers, `--shadow-raised`, panel radius 14, height 40, padding 6. Tools are Icon buttons, 28×28 ghost; the selected tool uses `--press` with an `--accent-text` icon. Done is a primary Button (`--accent` / `--on-accent`) with a ↵ keycap. Copy for AI is a secondary Button. No glass or `--surface` blur, per DESIGN §2.2a.
- Markup hint (design review D5): a pill 8 px above the toolbar, using keycaps on `--scrim` with `--on-scrim` text: `↵ done · ⌘Z undo · Esc discard` (Windows: `Enter`, `Ctrl+Z`). It is hidden while a text box is being edited. The wireframe's "Space: window · F full screen" line is not shown in the markup state.

**Shelf card actions (design review D2).**
- The action bar keeps 4 slots: **Copy · Copy for AI · Phone · More ▾**.
- More ▾ holds Edit (first), Copy link, Save as…, Reveal, Pin, Delete link and Delete.
- Edit also opens on double-click of the card or the `E` key. The `L` key still copies the link.
- DESIGN.md §3 (Action bar) and §7 (shelf keyboard) are updated to match in build step 1.
- Copy for AI uses the Lucide `scan-text` icon (16 px, 1.75 stroke), with no emoji (design review D6). It carries the label "Copy for AI" in the toolbar and a tooltip on the card. `scan-text` is added to the DESIGN.md §2.3 icon list.

**Edit surface.**
- Edit opens the overlay window on the monitor under the pointer. Behind it the live desktop is dimmed with the DESIGN overlay dim `rgba(0,0,0,0.35)` (design review D7), not a frozen frame.
- The item's original PNG is shown centred, scaled to fit 90% of that monitor (display scale only; geometry stays in image pixels), with the same toolbar under it.
- Any item source can be edited (capture, phone, clipboard, folder catch), because it is just a PNG.
- It differs from Approach A by reusing the overlay window and toolbar component: no new window type, no window chrome.

**Storage (shelf.db migration).**
- Add two nullable columns to `items`: `original_path TEXT` and `annotations TEXT` (JSON).
- `path` always points to the flattened PNG; `width`, `height`, `bytes` and `thumb_path` describe the flattened image.
- `original_path` is set the first time an item gets markup, either at capture time (Shift-release or the setting) or on its first Edit. The unmarked PNG moves to `originals/{id}.png`, a sibling of `captures/`, never inside it. That keeps `shelf::setup`'s `adopt_orphan_captures` (`shelf/mod.rs`), which adopts every `*.png` in `captures/`, from re-adding an unredacted original as a new item.
- Edit always re-flattens from `original_path` + `annotations`; it never draws on top of `path`.
- Commit order (eng review S3). Write the flattened PNG to `captures/{id}.png.tmp`, which adoption ignores. On the first markup, copy and fsync the original to `originals/{id}.png`. Rename the tmp file over `path`, rewrite the thumbnail, then update the row and the `item_remote_copies` changes in one SQLite transaction.
- Migration runner (eng review S2). The base `CREATE TABLE IF NOT EXISTS items` stays unchanged. Migration 1 runs when `PRAGMA user_version = 0`: the ALTERs, the new table and the backfill in one transaction, then it sets `user_version = 1`. New and existing databases take the same path.
- Module layout (eng review D2): `markup/` (`doc.rs`, `flatten.rs` with the bundled font), `cloud/remote_copies.rs` as the only module that reads or writes `item_remote_copies`, and OCR as `platform::recognize_text()` in `platform/macos.rs` and `platform/windows.rs` (no `ocr.rs` facade).
- New child table `item_remote_copies(item_id, kind TEXT CHECK (kind IN ('vault','drop')), remote_id TEXT, delete_token TEXT, state TEXT CHECK (state IN ('live','pending_delete')), created_at)`.
  - `item_id` has no foreign key and no cascade. Pending rows outlive their item (Delete, remove-after-drag, expiry or capacity trim) and keep retrying until confirmed. Once the card is gone, pending state shows as a line in Settings → Sync: "Removing N old copies".
  - Every vault upload (`cloud/vault.rs` `sync_capture_in_background` and `send_to_phones`, which today only log the id) and every drop records its remote id here.
  - `shelf::add_from_vault` (phone items arriving through `cloud/live.rs`) inserts a `('vault', item id, 'live')` row in the same transaction as the item.
  - Migration backfill:
    - phone rows come from `items.id WHERE source = 'phone'` (`items.vault_item_id` is never written today, so it can't be used);
    - drops come from every row with `drop_id` set and `drop_expires_at` in the future (`'drop'`, `drop_id`, `drop_delete_token`, `'live'`).
  - Pre-0.2.0 vault uploads were never recorded and are **not** backfilled (eng review D1). They expire on the server within 7 days because every upload carries the item TTL (`cloud/vault.rs:347`, `:425`). On the first Edit of an item created before the migration that may have been synced, the toolbar shows once: "Copies sent before this update stay on your phone until they expire (up to 7 days)." (DESIGN §5). Drops are still backfilled from `items.drop_*`, and phone items from `source = 'phone'`.
- Migration: `ALTER TABLE items ADD COLUMN` ×2 plus `CREATE TABLE item_remote_copies`, guarded by `PRAGMA user_version`.
- The expiry/capacity job deletes `path`, `original_path` and `thumb_path` (F2.7: nothing left after expiry).

**Overlay sessions.**
- One overlay session runs at a time, capture or Edit.
- The item open in Edit is held. The expiry and capacity sweep skips it, and it is swept on the first pass after the session closes (eng review D7). If the user deletes it from the shelf mid-edit, Done finds no row, removes the `.tmp` file and shows "That screenshot was removed, so your markup wasn't saved." (DESIGN §5).
- While Edit is open, the capture hotkey and tray "Capture" are ignored, and the Edit toolbar shows "Finish or press Esc to capture".
- While a capture overlay is up, shelf Edit buttons are disabled.
- Clicking Edit on another card while an Edit session is open focuses the open session; it never opens a second one.

**Annotation document.**
- `{"version":1,"items":[…],"transform":{…}}`, typed and validated in Rust (serde).
- Bounds (eng review D6): at most 500 annotations, 5,000 points per stroke (the UI simplifies longer ones), text up to 2,000 characters and 50 lines, stroke width 1–64 px, geometry clamped to the original image, JSON up to 1 MB.
- Geometry is in physical pixels of the original PNG, origin top-left, before any crop or rotation.
- The UI converts pointer positions from logical px using the image's display scale before sending.
- Crop/rotate is a separate `transform` (`crop` rect in original pixels, `rotate` 0/90/180/270), applied last at flatten time.
- `version` lets a later live renderer (Approach B) read the same documents unchanged.

**Rendering.**
- The UI draws a disposable SVG preview while you edit (view state only).
- Rust flattens on Enter/Done, writes the PNG and owns the result, so the redaction behaviour below never depends on UI code.
- Rasteriser: `tiny-skia` (antialiased paths with real stroke widths, round caps and joins, alpha blending for the highlighter) on the `image` buffers the app already uses. Text uses `ab_glyph` with one bundled font (Inter, OFL).
- New dependencies: `tiny-skia` and `ab_glyph`, each the smallest crate that does its job (rule 5).
- Fidelity rule: the flattened PNG is the source of truth.
  - Rust defines the geometry once in `markup::geometry()`: stroke widths, arrowhead = a triangle 4× the stroke long at a 30° half-angle, the step-badge circle, text line height 1.25. The overlay gets these values from the `markup_geometry` command when it opens, and the SVG preview uses only those values, never its own copy (eng review D3).
  - The SVG preview loads the same Inter file through `@font-face`.
  - Text is single-style, with line breaks only where the user typed them (no auto-wrap).
  - Tier 1 text covers only the code points in the bundled Inter (Latin, Greek, Cyrillic). Rust exposes that coverage set and validates every text annotation against it. The text field rejects other characters as they are typed (including Devanagari, CJK and emoji, which the webview would otherwise render through system fallback), and shows "This character isn't supported in text yet" (DESIGN §5). So the preview never shows a glyph the flatten can't draw.
  - Cargo golden-image tests pin each tool's output.

**Redaction behaviour.**
- Every outgoing path reads only the flattened `path`, never `original_path`: clipboard copy, drag staging in `drag/`, Save as…, QR drop, share link, vault auto-sync, and Copy for AI (image and OCR input).
- The redact tool defaults to **Solid**, an opaque fill that removes every original pixel in the region.
- **Pixelate** and **Blur** are offered as "Obscure", not as secure redaction. Pixelated text can be recovered by known-font attacks (e.g. Depix, Unredacter), so the tool's tooltip says "Hides detail. Use Solid to fully hide text."
- Pixelate uses a block of at least half the region's shorter side. Blur is a fast downscale-then-upscale, with no Gaussian.
- Editing an item that already has remote copies (rows in `item_remote_copies`):
  1. The edit commits locally at once and clears `items.drop_*` (`clear_drop`) in the same step, before any remote call. That way `drops::send` can never hand back the old live drop, and the next share mints a fresh drop from the flattened `path`.
  2. Each remote copy is marked `pending_delete` and deleted: vault copies with `delete_item`, drops with `DELETE /drops/{id}` and their delete token. A copy counts as removed only on 204, 404 or 410.
  3. Pending deletions retry until confirmed: on app start, on every live-socket (re)connect, and on each 10-minute expiry sweep (eng review D4). The card shows a small warning dot until then.
  4. If the item was synced before, the flattened PNG is uploaded once under a new vault id after the deletions are confirmed.
  5. Phone-origin items follow the same steps: their phone-side vault copy is deleted.
  6. Microcopy (DESIGN §5): on confirmed removal, "Old link removed. Share again for a new one."; while still pending, "Couldn't remove the old copy yet. Hopshot will keep trying."
- Committing an edit also calls `files::remove_staged(id)`, so a drag staged before the edit can't serve the old pixels.

**Keys.**
- Selecting (before release): unchanged. Space toggles window mode, F captures the monitor, Esc cancels.
- Markup state:
  - Space and F do nothing.
  - Tools: V select, A arrow, R rectangle, O ellipse, T text, P pen, H highlighter, N numbered step, B blur, C crop.
  - Cmd/Ctrl+Z undo; Shift+Cmd/Ctrl+Z (and Ctrl+Y) redo.
  - Delete/Backspace removes the selected annotation.
  - Enter or Done finishes.
- While typing text: every key goes to the text field except Esc (leave text), Enter (finish this text; Shift+Enter for a new line) and Cmd/Ctrl+Z.
- Esc ladder:
  1. Leave text editing.
  2. With annotations present: a hint "Press Esc again to discard", and the second Esc discards the markup.
  3. With no annotations: close. At capture time that cancels the capture, as today; from Edit it leaves the item unchanged.

**Copy for AI.**
- Runs only when pressed, from a shelf-card action or a toolbar button.
- The toolbar button acts as Done first: Rust flattens and commits the item to the shelf, and the overlay closes. Recognition then starts on the new `path`. OCR never reads `original_path` or the unflattened screen.
- Recognition is asynchronous on a worker thread (Apple Vision; Windows.Media.Ocr) on the flattened image; the button shows a spinner.
- Recognized text is never logged, stored, synced or sent anywhere. It exists only in the clipboard write.
- Microcopy (DESIGN §5):
  - "Copied image + text";
  - no text found: "No text found. Image copied.";
  - no recognizer (Windows OCR language pack missing): "Text reading isn't available on this PC. Image copied."
- Clipboard behaviour depends on the step 2 spike result.
- Overwrite guard (eng review D5): Rust records the OS clipboard change counter when Copy for AI is pressed and writes after OCR only if the counter is unchanged. Otherwise the shelf shows "Text ready · Copy text" for 10 s.
- Windows: the flattened image is scaled to fit `OcrEngine.MaxImageDimension` before recognition. The clipboard image itself is never scaled (eng review A4, to verify in the step 2 spike).
- New dependencies:
  - `windows` crate (features `Media_Ocr`, `Graphics_Imaging`), Windows only;
  - `objc2-vision`, macOS only.
  - Both are justified as the only on-device OCR APIs, keeping rule 1.

### Section 1: Architecture

Two shapes for `markup/`:
- Shape 1, pure (picked). `markup::validate(doc) -> Result<Doc>`, `markup::flatten(original: &RgbaImage, doc: &Doc) -> RgbaImage`, `markup::geometry() -> Geometry`. No files, no store, no network. `shelf::apply_markup(app, id, doc)` owns the commit transaction (S3), and `cloud::remote_copies` owns cleanup.
- Shape 2, owning. `markup::commit(app, id, doc)` does flatten, files, row and remote cleanup itself.
