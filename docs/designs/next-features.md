### 0.1.16: background tool (target Mon 1 Dec; re-estimated from 28 Nov, see below)
- **Estimate (CC-assisted, one person):** 3 days.
  - The shared Edit surface: 1 day. It doesn't exist yet, and markup's Edit will reuse it in 0.2.0, so 0.2.0 depends on it.
  - Compose and controls: 1 day.
  - Migration 1, storage and tests: 1 day.
  - Starting Wed 26 Nov, that's Fri 28 Nov at best, so the target is **Mon 1 Dec** with a day of buffer. Founder to confirm.
- **Entry:** a card's More ▾ → **Background**, or `B` on the selected card.
- **The shared Edit surface (built here):**
  - A new `edit` mode of the existing `overlay-{n}` windows, on the monitor under the pointer. No new window type.
  - Rust emits `overlay:edit` with the item's image URL (served through the existing `frame://` protocol from the item's file, never a new HTTP path) and the panel kind (`background` now, `markup` in 0.2.0).
  - The window shows the live desktop dimmed with the DESIGN overlay dim (no frozen frame), the image centred at up to 90% of the monitor, and the panel to its right. It takes focus like the capture overlay, and Esc closes it unchanged.
  - Only one overlay session at a time, capture or Edit (as in the 24 Nov design). While it's open, the capture hotkey is ignored.
- **Controls** (wireframe):
  - 6 backgrounds: none, 4 soft solids, 1 orange gradient. Exact colours become DESIGN tokens in the design review.
  - Padding S/M/L.
  - Corner radius slider, 0–24 px.
  - Shadow on/off.
  - Size Auto / 16:9 / 1:1.
  - Cancel, and Done ↵.
- **Storage:**
  - Migration 1 (`PRAGMA user_version` 0→1, base CREATE unchanged, one transaction) adds:
    - `items.original_path`, `items.style` (JSON), `items.pending_style` (JSON), and `items.annotations` (unused until 0.2.0);
    - a `superseded_drops` table (`drop_id`, `delete_token`, `expires_at`) for share links replaced by an edit whose delete hasn't succeeded yet.
  - The original lives in `originals/{id}.png`, never in `captures/` (orphan adoption).
  - Re-opening Background re-renders from `original_path` + `style`; it never frames a framed image.
- **Crash-safe commit order on Done:**
  1. If `original_path` is unset, copy the current file to `originals/{id}.png.tmp`, fsync, and rename it to `originals/{id}.png`.
  2. Transaction A: set `original_path` and `pending_style` (the new style). `path` is untouched.
  3. Render the framed PNG from `original_path` + `pending_style` to `captures/{id}.png.tmp` (adoption ignores it, since only `*.png` is listed), fsync, and rename it over `path`.
  4. Transaction B: set `style` = `pending_style`, clear `pending_style`, set `width`, `height` and `bytes` from the new file, and rewrite the thumbnail.
- **Startup recovery (roll forward):**
  - Any row with `pending_style` set had a Done interrupted at step 3 or 4. Recovery re-runs steps 3 and 4 for it. The render is deterministic from `original_path` + `pending_style`, so re-running is safe whether or not the rename had already happened.
  - A row whose `path` is missing but whose `original_path` exists gets the original copied back to `path`, with `style` and `pending_style` cleared.
  - Any `originals/*.png` that no row references is deleted, and so is any leftover `*.png.tmp`.
- **Every item-removal path deletes `path`, `original_path` and `thumb_path`:** Delete, Remove after drag, expiry, the capacity drop-off and "delete all". They all go through `shelf::expiry::remove_files`, which gains `original_path`.
- **Share link (drop) on Done:**
  - Rust tries `DELETE /drops/{id}` with the stored delete token.
  - On 204/404/410, `clear_drop` runs.
  - On any other result (offline, server error), the drop's id, token and expiry move into `superseded_drops` and `clear_drop` runs.
  - Either way, the next Copy link or Send mints a new link with the framed image. `drops::send` never reuses the old one, because the item no longer has a drop.
  - Superseded deletes are retried at startup and whenever a cloud call next succeeds. Rows are removed on 204/404/410 or once they expire.
  - "Delete all my cloud data" deletes every `superseded_drops` row as well as `live_drops`.
  - Until a retry succeeds, the old link still shows the version without the background. A background is not a redaction, so that's not a privacy problem, and the link expires on its own.
- **Phone copies (vault) on Done:**
  - No re-upload and no deletion. Paired phones keep the version without the background until it expires (at most 7 days, the item TTL).
  - Send to phone after Done uploads the framed image as a new vault item, which counts against `sync.vaultUploadsPerDay` like any send.
  - Done never triggers auto-sync.
- `files::remove_staged(id)` runs on Done, so a drag staged earlier can't serve the file without the background.
- **Rendering:** Rust composes the result with `tiny-skia`: antialiased rounded-corner mask, gradient fill, and a shadow from a blurred alpha mask. `tiny-skia` is already approved for markup (rule 5 justification on 24 Nov), so it lands now and is shared later.
- **Gating:** free on every plan. It isn't a capture and never calls `record_capture`, same as Edit (D7).
- **Remembered choice:** the last style is saved in settings. Opening Background again starts with it, so the second time it's one click (Done).
- **DESIGN.md updates in this release:** the Edit surface, the Background panel and its tokens, and in §5 the string "That image is too big to send. 10 MB is the limit." (today it exists only in `cloud/client.rs`), plus the card's "Too big to sync" chip state. The 10 MB in both comes from `limits.lifetime.maxImageBytes`. Framing can push an image over the limit, so the oversize check (see 0.1.17, "Over the send limit") ships here.

### 0.1.17: scrolling capture (target Sat 6 Dec)
- **Estimate (CC-assisted, one person), starting Tue 2 Dec:** 3.5 days.
  - Day-1 spike and session windows (border strips, HUD, temporary keys): 1 day.
  - Stitcher and its unit tests: 1 day.
  - Limits, timeouts, the clipboard threshold and memory bands: 0.5 day.
  - Manual matrix on both OSes and fixes: 1 day.
  - That's Fri 5 Dec at best, so the target is **Sat 6 Dec** with half a day of buffer.
  - The oversize-upload check ships in 0.1.16, so it isn't counted here.
  - If the spike fails and needs more than half a day of fixes, the live preview strip is cut first. The HUD then shows only the size label and Done / Cancel.
- **Gate on day 1 (spike, both OSes):** run a scroll session over a busy page and check that no Hopshot pixel appears in any grabbed frame. Test a small region and a region that fills the monitor. If a pixel appears, fix the chrome placement below before writing the stitcher.
- **Entry:**
  - In the capture overlay, drag an area, then press `S`.
  - Or tray → **Scrolling capture**, which calls `capture::start(Mode::Scroll)`. That opens the normal region overlay with the hint "Drag the area to scroll-capture". The Free-plan `paused()` check and the Screen Recording permission check apply exactly as for any capture.
- **The user scrolls; Hopshot doesn't auto-scroll** (wireframe, approved). This avoids a new macOS Accessibility permission. Auto-scroll is a later option.
- **Session start:**
  - Every `overlay-{n}` window is hidden, on all monitors, so nothing covers or swallows input.
  - The frozen frames are dropped.
  - Session windows appear, all **entirely outside the grabbed region**:
    - **Border:** four 2 px strip windows, one along each edge, just outside the region. They ignore all cursor events (`set_ignore_cursor_events(true)`). A strip that would fall off the monitor isn't drawn.
    - **HUD:** a non-activating panel (macOS NSPanel non-activating; Windows `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`, as the shelf already uses). It holds the hint, the size label, the live preview strip and **Done** / **Cancel** buttons. Clicks work without taking focus from the app being scrolled.
  - **HUD placement**, first that fits:
    1. right of the region, then left, below or above, on the same monitor;
    2. the same, in a compact bar (44 px tall, no preview strip);
    3. on another monitor, if there is one;
    4. otherwise, the bottom 44 px of the selection are given to the compact bar. The grabbed region shrinks by that much, and the border shows the smaller area before scrolling starts.
  - All session windows are also excluded from screen capture (macOS `NSWindowSharingNone`; Windows `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`). Correctness doesn't depend on that, because no window ever overlaps the grabbed region.
- **Keys:**
  - For the session only, Hopshot registers temporary global shortcuts for Enter (finish) and Esc (cancel) through the existing global-shortcut plugin. Every exit path unregisters them: finish, cancel, error and timeout.
  - While a session runs, Enter and Esc don't reach the app being scrolled. That's acceptable because the user is scrolling, not typing, and the hint says "↵ done · Esc cancel".
- **Grabbing:** Rust re-grabs the selected region of that monitor live, using its own scale factor, about every 120 ms. It keeps a frame only when it differs from the last grab.
- **Stitching (pure Rust, unit-tested on every OS):**
  - The reference is always the **tail of the stitched output** (its last frame-height of rows), never simply the last grab.
  - Each new frame is matched against that tail by row hashes, excluding sticky top and bottom bands (rows identical across 3+ frames).
  - A frame whose content is at or above the tail adds nothing (scrolled back or not moved). Only rows below the tail are appended.
  - If a frame has no overlap with the tail ("scrolled too fast"), the hint shows "Scrolled too fast, scroll back a little" and the frame isn't used.
- **Limits:**
  - Two constants (performance guards, not plan limits, so not in `config/limits.json`): stitched height ≤ 20,000 **physical** px, and stitched area ≤ 32,000,000 physical px.
  - Whichever is reached first finishes the session automatically.
  - **Memory layout:**
    - The output is a list of appended row bands (one `Vec` per frame's new rows), so nothing ever reallocates or copies the whole image.
    - The tail reference is kept as one 64-bit hash per row, not as pixels.
    - The PNG is encoded by streaming the bands row by row (`png` stream writer) into a buffered file, never as a full encoded buffer in memory.
  - **Peak memory:** at 32 MP the bands are 32,000,000 × 4 B ≈ 122.1 MiB. Two full 4K-wide frames are 2 × 3,840 × 2,160 × 4 B ≈ 63.3 MiB. Row hashes and encoder buffers are under 8 MiB. That totals about 193 MiB, only during the session.
- **Timeouts:**
  - No new rows for 60 s: the session finishes automatically if it has at least one frame, and cancels otherwise.
  - Hard maximum of 5 minutes.
- **Finish:** Enter or Done → `deliver()` with the stitched PNG: shelf, one `record_capture` (counts as one capture on Free).
  - Clipboard (`copy_on_capture`) applies only up to 16,000,000 px. Above that, Hopshot skips it and shows "Too tall to copy. Drag it from the shelf instead." This release adds that string to DESIGN.md §5.
  - Esc or Cancel records nothing.
- **Memory:** frames are dropped as soon as their new rows are copied into a band. Only the bands, the tail hashes, the previous grab and the latest grab are held.
- **Over the send limit** (applies to both features; ships in 0.1.16):
  - Before any upload (auto-sync, Send to phone, Copy link), Rust checks the PNG's size against `limits.lifetime.maxImageBytes` from `config/limits.json` (10 MB today).
  - Over the limit: no upload is attempted. Send and Copy link show the existing DESIGN §5 string "That image is too big to send. 10 MB is the limit." Auto-sync skips that item and puts a small "Too big to sync" chip on its card.
  - Drag and Copy to clipboard are unaffected.

### R2-1 — completeness (blocking)

**Problem**

On /hopshot-vs-cleanshot-x/: the lead paragraph ('if you annotate, record or take scrolling screenshots, it's the one to buy'), the 'Stay with CleanShot X if' bullet 'You need scrolling capture or text recognition (OCR)', and the visible 'Updated 23 November 2026' line. On /cleanshot-x-for-windows/: the 'Scrolling capture' row's 'Other apps that do it' column (ShareX, Snagit, PicPick) and the 'Annotate: arrows, text, blur' row.

**Remedy**

> Extend the list to every Hopshot claim on both pages: the lead, the 'Stay with CleanShot X if' bullets, the visible Updated line, and the 'Other apps' column. Split the combined row into one row per feature (annotation, recording, scrolling capture, OCR), so each can flip on its own Go live.

### R2-2 — feasibility (blocking)

**Problem**

> The border is one window 2 px larger than the region on each side, so it covers the whole region, with a transparent interior. That contradicts 'both strictly outside the selected region' and 'Correctness doesn't depend on that, because neither window overlaps the region'. Correctness then does depend on the interior being fully transparent (alpha 0, no window shadow, no WebView2 background) on both OSes, or on capture exclusion.

**Remedy**

> Either draw the border as four thin windows that sit entirely outside the region, or say the border window overlaps the region, needs an alpha-0 interior with shadow off, and is checked by the day-1 gate. Then correct the 'neither window overlaps' sentence.

### R2-3 — completeness (blocking)

**Problem**

> When the selection fills most of the monitor (for example a full-width or full-height browser area), there is no room to the right, left or below. Clamping then puts the HUD inside the region, where it shows up in every grab unless capture exclusion works, and the doc says correctness does not depend on exclusion. Nothing covers this case.

**Remedy**

> Add 'else above' and a final fallback for when nothing fits: the HUD goes on another monitor, or the region is shrunk by the HUD's size, or the HUD is hidden during each grab. Add it to the day-1 gate.

### R2-4 — feasibility (blocking)

**Problem**

> The peak memory figure is too low. Output buffer: 40,000,000 px × 4 B = 160,000,000 B ≈ 152.6 MiB. A grabbed frame for a full 4K-wide region: 3,840 × 2,160 × 4 B = 33,177,600 B ≈ 31.6 MiB, so two frames are ≈ 63.3 MiB. Sum: 152.6 + 63.3 ≈ 215.9 MiB before the PNG encode buffer. If the output Vec grows by reallocation, the old and new buffers coexist (for example 76 + 153 MiB ≈ 229 MiB at the last doubling). The stated bound of about 200 MiB is not met.

**Remedy**

> Recompute the peak with the real inputs and state it, or lower the area cap so the bound holds. Preallocate or chunk the output so it never reallocates, and say whether the PNG encode streams or holds a full encoded buffer.

### R2-5 — feasibility (blocking)

**Problem**
